在大多数软件中，崩溃意味着故事的结束。但在《宝可梦 红／蓝》（1996 年）中，特定类别的崩溃却是故事的开始。玩家们发现，游戏中未经检查的物品栏数组可以越界访问，其边界之外的字节可以像普通物品一样被读取和写入，并且——通过特定顺序的错误物品（Glitch items）——可以让 Sharp SM83 CPU 将玩家控制的数据当作指令来执行。

这并不是一个隐喻意义上的“小故障（Glitch）”。严格来说，这是真正的内存破坏（Memory Corruption）：一种越界数组访问，它最终将程序计数器（PC）重定向到攻击者控制的 RAM 中。几十年后，同样的漏洞类型也会出现在 x86 和 ARM 目标的缓冲区溢出中。Game Boy 版本规模足够小，并且经过速通（Speedrunning）和逆向工程社区的彻底记录，使得我们能够从第一个被破坏的字节一直追踪到完整的代码执行。

## 1. Game Boy 硬件限制与内存映射

Game Boy 的逻辑主板围绕 **Sharp SM83** 构建，这是一个融合了 Intel 8080 指令集和 Zilog Z80 扩展子集的定制核心，主频约为 4.194304 MHz。它暴露了一个 8 位数据总线和一个 16 位地址总线，为 CPU 提供了平坦的 64 KB 地址空间（`$0000-$FFFF`），且没有内存保护、没有特权环（Privilege Rings）、也没有执行权限位。只要能将程序计数器（PC）引导到那里，CPU 读取的任何字节都可以被强制执行。

| 地址范围 | 区域 | 备注 |
|---|---|---|
| `$0000-$3FFF` | ROM 0区 | 固定卡带 ROM 库 |
| `$4000-$7FFF` | ROM N区 | 可通过 MBC 切换 |
| `$8000-$9FFF` | VRAM | 图块（Tile）与地图数据 |
| `$A000-$BFFF` | 外部 RAM (SRAM) | 电池供电的存档数据 |
| `$C000-$DFFF` | 工作 RAM (WRAM) | 8 KiB 通用 RAM；玩家、同行宝可梦及道具状态存放在此 |
| `$E000-$FDFF` | 回显 RAM (Echo RAM) | 镜像 `$C000-$DDFF`；仅连接了低 13 位地址线 |
| `$FE00-$FE9F` | OAM | 精灵属性表（Sprite Attribute Table） |
| `$FF00-$FF7F` | I/O 寄存器 | 内存映射硬件（手柄、音频、PPU、定时器） |
| `$FF80-$FFFE` | 高速 RAM (HRAM) | 127 字节的高速 RAM，DMA 期间唯一的安全暂存空间 |
| `$FFFF` | IE 寄存器 | 中断使能标志（Interrupt Enable） |

<Alert variant="info">
**设计上无内存保护：** SM83 没有 MMU、没有等效的 DEP（数据执行保护），也没有硬件层面的边界检查。游戏所表现出的每一项安全属性，都是游戏自身代码的属性，而不是底层芯片的属性。如果物品栏例程忘记检查索引，其下层的任何机制都不会捕获这个错误。
</Alert>

![展示 ROM、VRAM、WRAM、OAM 和 HRAM 区域的 Game Boy SM83 CPU 与 WRAM 内存映射图](../../../assets/blog/gameboy-ace/1.webp)
*图 1：Game Boy 的 16 位地址空间。WRAM（`$C000-$DFFF`）将所有可变的玩家状态（包括道具背包）保存在一个单一的、没有结构间隔离的未分化区块中。*

面向玩家的状态——同行宝可梦、图鉴标志、地图坐标以及道具背包——从 `$D163` 附近开始按顺序打包到 WRAM 中。除了读写它们的底层代码所遵循的规范之外，没有任何东西将一个结构与下一个结构隔离开来。

## 2. 物品栏机制与数组越界

道具背包占据了从 `$D31D` 开始的一个固定大小的 WRAM 块。其布局是一个带有长度前缀的扁平数组：

- `$D31D` — 总物品数量（1 字节）
- `$D31E`, `$D31F` — 物品槽 1：`[物品 ID, 数量]`
- `$D320`, `$D321` — 物品槽 2
- ……总共 20 个槽位，止于 `$D344`/`$D345`
- `$D346` — 列表终结符（Terminator），预期应包含 `$FF`

20 个槽位是*菜单*强制施加的限制——而不是底层数组逻辑所强制的限制。光标和滚动例程在决定迭代多远时，真正信任的是 `$D31D` 处的数量字节。如果该字节在没有与之匹配、正确限定边界的数组的情况下被增大到 20 以上，那么任何遍历背包的例程都会越过 `$D346` 进行读写并继续执行。

这是通过**255堆叠物品复制漏洞（255-stack item duplication glitch）**实现的：通过利用游戏在处理堆叠数量为 255 的物品周围的一系列特定“背包/丢弃/交换”输入序列时的缺陷，玩家可以使背包中最顶部的“物品”变成菜单自身的“取消（Cancel）”条目，并使 `$D31D` 处的总物品数量字节向下溢出（underflow）至接近 `255`。此时，游戏认为背包中包含 255 个条目。当滚动超过第 20 个槽位时，它不会停止；而是直接进入 WRAM 中 `$D346` 之后恰好存在的任何字节，将它们显示为物品名称，并把它们当作可交换、可丢弃的任意背包条目来处理。

<Alert variant="warning">
**这是索引验证失败，而非传统意义上的缓冲区溢出：** 纯粹拥有过多物品并不会导致在数组之外发生写入。真正的破坏在于*边界本身*——即数量字节——受攻击者控制，并且没有针对固定的 20 个槽位分配进行检查，因此由其计算出的每一个后续数组访问都会落在结构预期范围之外。
</Alert>

![展示物品背包数组如何下溢其 20 槽位边界并侵入相邻 WRAM 结构的图表](../../../assets/blog/gameboy-ace/2.webp)
*图 2：一旦物品数量字节超过了 20 槽位的分配，背包的滚动和交换例程就会直接索引到玩家的金钱、地图数据及更远的地方——所有这些都可以作为虚假的“物品”进行寻址。*

## 3. 越界内存破坏 (Out-of-Bounds Memory Corruption)

由于 WRAM 在硬件层面上没有结构边界，紧跟在道具背包后面的字节只是开发人员碰巧放在那里的下一个字段。在英文版中，其布局延续如下：

| 地址 | 结构 | 暴露为（虚假的）物品槽 |
|---|---|---|
| `$D346` | 预期的背包终结符（`$FF`） | 槽位 21 ID |
| `$D347-$D349` | 玩家金钱（3 字节，BCD 编码） | 槽位 21-22 |
| `$D34B` 及之后 | 游戏厅硬币盒、徽章、信件/姓名缓冲区 | 槽位 23+ |
| WRAM 更深处 | 当前地图 ID、玩家 X/Y 坐标、传送表（Warp tables）、背景图块索引 | 更深的槽位 |
| 更深处 | 精灵/音频状态、野生宝可梦遭遇缓冲区 | 更深的槽位 |

由于扩展后的背包将这些字段暴露为普通的 `[ID, 数量]` 对，玩家可以像处理伤药（Potion）一样“丢弃”或“交换”它们——如果将其应用到金钱字节上，就可以直接修改货币；如果应用到地图坐标字节上，则可以将玩家传送或直接跃迁至名人堂（Hall of Fame）动画序列。这已经是一项非常强大的能力：完全通过菜单输入就能实现**对 WRAM 的近乎任意的读写访问**。宝可梦社区将这种特定能力称为**道具下溢（item underflow）**——它不同于真正的代码执行，但却是后者的先决条件。

<Alert variant="warning">
**读写访问尚不等于代码执行。** 破坏金钱或坐标字节只会改变游戏随后仍会将其解释为数据的*数据*。它不会导致 SM83 将这些字节中的任何一个获取并作为指令执行。这需要第二个、独立的故障：即游戏本身将其解引用（dereference）为跳转目标的指针。
</Alert>

![对比物品下溢内存读写能力与需要被劫持的跳转指针的真正代码执行的流程图](../../../assets/blog/gameboy-ace/3.webp)
*图 3：物品下溢赋予了任意内存读写能力。若要将该能力升级为指令执行，则需要另一个独立的漏洞——即可被破坏的效果指针（effect pointer）。*

## 4. 劫持程序计数器 (PC)

第一世代的道具使用例程并没有为每个道具调用单一的通用处理程序。每个道具索引都带有有一个**效果指针（effect pointer）**——这是引擎在使用该道具时跳转到的 16 位地址，因此伤药（Potion）、精灵球（Poké Ball）和技能机（TM）各自可以运行不同的代码。普通道具指向 ROM，那里仅存放合法的道具效果例程。但是，道具表本身只是一组由单字节索引的数据，并且前面描述的**扩展道具背包**允许玩家创建其索引号本不该被访问到的道具——即“错误物品（Glitch items）”。

这些错误物品中有少数几个具有解析为*可写 WRAM* 而非 ROM 的效果指针。在英文版本中最著名的是道具索引 `0x5D`，根据其受损的屏幕名称被昵称为**“8F”**。它的效果指针指向 `$D163`——玩家**同行宝可梦数据**的起始处。从背包中使用“8F”不会运行伤药风格的动画；它会导致 SM83 从 `$D163` 获取下一条指令并执行那里存在的任何字节，因为游戏自身的代码刚刚执行了 `JP $D163`（或同等指令），而没有验证目标是否在 ROM 中。

从那一刻起，同行宝可梦数据——种族 ID、属性字节、努力值（EV）、招式槽，甚至附近存储的昵称——都被当作 SM83 操作码流来读取。能够控制这些字节的 TAS 选手或研究人员（通过捕捉或交换特定宝可梦、分配特定的属性经验值、或将宝可梦重命名为选定的字节串）就能控制 CPU 接下来执行的指令流。

<Alert variant="info">
**为什么昵称很重要：** 宝可梦的昵称在保存后作为原始字节存储，没有进一步的验证，并且命名界面允许玩家通过特定的输入技巧选择几乎任何字节值。从功能上讲，昵称就是玩家可以放置在同行宝可梦结构受损入口点旁边的一个小型可写代码穴（code cave）。
</Alert>

![展示错误物品的效果指针将 SM83 执行从 ROM 重定向到 WRAM 中同行宝可梦数据的流程图](../../../assets/blog/gameboy-ace/4.webp)
*图 4：使用“8F”错误物品会解引用一个从未针对“效果指针总是指向 ROM”这一假设进行过审查的效果指针，从而将程序计数器重定向到可写的同行数据中。*

## 5. 汇编代码片段与解析

一旦执行流落入同行宝可梦数据中，那里的字节必须同时充当合法的 SM83 操作码才能执行任何有用的操作。一个最小化的引导程序（bootstrap）通常旨在将执行流重新指向更大且更容易控制的地方——例如物品背包本身，玩家可以在其中逐个槽位地自由重写——然后再运行真正的有效负载（payload）。下面的代码片段勾勒出了该引导程序的形态：一段放置在同行结构首个可控字节中的短序列，它将一个值加载到累加器中，然后执行无条件跳转，跳入作为道具 ID/数量对形式暂存了更长有效负载的物品背包区域。

export const z80CodeSnippet = `; ace_bootstrap.asm
; 通过 "8F" 错误物品损坏的效果指针，
; PC 降落到 $D163 后执行的最小引导程序。
; 编码为同行数据字节（种族/属性字段兼作操作码）。

        ; 入口点：$D163 (wPartyCount - 执行流直接滑入种族/属性字节)
        LD   A, $00        ; 3E 00  -- 操作码 0x3E = LD A, n (8080/Z80/SM83)
        NOP                ; 00     -- 用于保持后续字段对齐的填充
        NOP                ; 00
        NOP                ; 00

        ; 将执行流重定向到物品背包 ($D31E)，玩家可以通过普通的菜单输入
        ; 在该背包中自由重写——从而将背包变成真实有效负载的暂存区。
        JP   $D31E         ; C3 1E D3  -- 操作码 0xC3 = JP nn

; --- 以库存 [物品 ID, 数量] 对形式暂存的有效负载 ---
; 一旦执行流到达 $D31E，下面的每一对都将被读取为两个原始字节，
; 因此物品选择兼作操作码流。
;
;   槽位   字节     解码
;   1      3E 05    LD A, $05
;   2      47 00    LD B, A ; NOP (填充)
;   3      C9 00    RET     ; NOP (填充)
`;

相关的编码细节是，`0x3E` 是 SM83 的 `LD A, n` 操作码——将一个立即数字节加载到累加器中——它毫无修改地继承自 Intel 8080。物品的索引字节和数量字节（玩家通过在菜单中靠近并选择特定的堆叠数量来设置）一旦被程序计数器指向，在硬件层面上就与两字节的 `LD A, n` 指令毫无二致。这个漏洞的精妙之处在于*没有任何作弊设备或外部工具向 WRAM 写入数据*——有效负载的每一个字节都是通过完全普通（尽管极其精准）的游戏输入放置在那里的。

## 6. 系统架构影响

第一世代的物品下溢到 ACE（任意代码执行）攻击链是三个独立故障复合演变成完全代码执行的教科书级范例：一个未经验证的长度字段驱动数组遍历越过了其内存分配边界；一个将攻击者可写的 RAM 视为合法跳转目标的数据/控制流边界；以及一个足够宽容、使得普通游戏数据在语法上也能成为有效机器码的指令集。这些故障并不稀奇——它们与几十年来在更大型系统上出现的原生缓冲区溢出 CVE 背后的根本原因完全相同。Game Boy 只是没有 DEP（数据执行保护）、没有 ASLR（地址空间布局随机化）、没有栈金丝雀（Stack Canaries），也没有特权分离来从中阻挠，因此仅凭反汇编和一个存档状态，整个攻击链便可以从头到尾清晰可见。

更广泛的教训超越了 1996 年的硬件：任何信任长度或计数值而未针对其实际分配的内存进行验证的系统，都距离通过某个输入序列将相邻结构暴露为攻击者控制的数据只有一步之遥——而且，如果这些相邻结构中的任何一个被解引用为代码或指针，就会失去全部的执行控制权。

## 技术术语表

| 术语 | 定义 |
|---|---|
| **任意代码执行 (ACE / Arbitrary Code Execution)** | 将程序的程序计数器重定向到攻击者控制的数据并使其作为指令执行的能力。 |
| **程序计数器 (PC)** | 持有要获取和执行的下一条指令地址的 CPU 寄存器。 |
| **Sharp SM83** | Game Boy 的定制 CPU 核心，结合了 Intel 8080 和 Zilog Z80 指令子集，主频约 4.19 MHz。 |
| **工作 RAM (WRAM / Work RAM)** | Game Boy 的 8 KiB 通用 RAM 区域（`$C000-$DFFF`），保存所有可变的游戏和玩家状态。 |
| **效果指针 (Effect Pointer)** | 道具使用例程跳转到的每个道具专属的 16 位地址；通常指向驻留在 ROM 中的道具效果代码。 |
| **道具下溢 (Item Underflow)** | 第一世代漏洞，通过将背包的物品计数字节破坏到超出其 20 个槽位分配的范围，从而授予对 WRAM 的近乎任意的读/写访问权限。 |
| **错误物品 (Glitch Item)** | 索引号超出游戏预期有效范围的道具，仅通过内存破坏才能达到，通常带有指向 RAM 的效果指针。 |
| **操作码 (Opcode)** | 标识特定 CPU 指令的字节值；在 SM83 上，`0x3E` 编码 `LD A, n`。 |
| **栈覆盖 (Stack Overwrite)** | 调用栈上返回地址或局部变量数据的破坏，在涉及精心构造的同行数据的其他第一世代 ACE 链中使用。 |
| **边界检查 (Bounds Checking)** | 在使用索引或长度计算地址之前，根据分配的内存的实际大小对其进行验证——这是贯穿整个漏洞利用链所缺失的控制机制。 |
